## 1. Verdict

The architecture review found a system whose storage layer is genuinely excellent and whose weakest seams are operational. This review finds the complementary problem, and it is the more consequential of the two: **evidence gets upgraded on its way from that sound storage layer to the agent-facing verdict.** Five separate mechanisms do it, and they compose.

A whole-file lexical match carries no symbol, so resolution binds it to whichever symbol in that file happens to have the lowest node id, and the answer cites that symbol's real name and line (CR-003). Every ordinary resolved hit is stamped `ResolvedGraph` / producer `route_endpoint` / `eligible_for_sufficiency = true` *before* its retrieval lane is known, and the decorator that would classify it correctly short-circuits on the tier already present — so a pure dense hit becomes graph proof (CR-004). The retrieval stage labelled `graph_neighbor` reads no edges at all; it is bidirectional substring containment between display names in the same file, which makes `Client`/`ClientConfig` and `run`/`runtime` proof-bearing neighbours (CR-005). Above 25,000 files, freshness checking is skipped entirely and the result is deliberately admitted, and — the sharp part — the sidecar fingerprint then mixes *live* file reads with *stale* core rows, so rebuilding the sidecar makes strict readiness pass and renders the drift probe dead code (CR-001). And a source file containing invalid UTF-8 is indexed into core with full symbols while its text is silently dropped from every text lane at once, with the incompleteness recorded, hash-bound, and then withheld from every readiness verdict (CR-068 — cited in revision 1 as "CR-006" by error, with no numbered entry behind it; one of two findings lost in the merge and restored in revision 2).

These matter more here than they would in an ordinary search tool, because this product's contract is stronger than search: it marks evidence `sufficient` and populates `avoid_opening`. The architecture review's ARCH-036 described claim *roles* being inferred from names; this review finds the evidence those claims rest on is itself upgraded three layers earlier. **The publication fence is strong. What the product does with evidence after publication does not consistently fail closed.**

Two other patterns run through the register. First, **unanchored string matching is the single most common defect class** — `find("id=")` mints entities from `data-testid`, `find("create table")` indexes commented-out DDL, `find('(')` reads a Java annotation's arguments as a method's parameters, `find('>')` truncates a `<script>` tag at a `>` inside a quoted generic. Each is one line; together they are eleven findings. Second, **hot paths repeatedly do whole-corpus work to answer a bounded question**: hashing the full model file on every wake from idle, re-digesting the entire structural corpus four times per publication, deep-scanning the whole FTS mirror twice per health probe *before* the query cache is consulted, cloning the full symbol-name map per resolution, and loading the entire edge table to find one node's handler.

The template pipeline deserves separate mention as the worst-affected subsystem: CR-002 (~86% of Svelte components permanently parser-partial, their deleted symbols never cleaned up), CR-071 (Astro typed frontmatter landing in the same retention path via wrong grammar selection), CR-007 (canonical ids keyed by basename, merging symbols across every `+page.svelte` and `index.vue`), and CR-046 (quote-unaware tag scanning feeding CR-002) compound into persistent index corruption for template-framework projects. (Revision 1 cited CR-008 and CR-013 in this chain — wrong entries; CR-013 is the unrelated HTML HashMap defect.)

## 2. High severity

**CR-001 — Repositories above 25,000 files are served with freshness unknown, and the sidecar rebuild makes the drift probe dead code** · `crates/codestory-runtime/src/index_freshness.rs:15-16,234-243,280-311`, `services.rs:786-795` (admission), `:681-709` (activation), `:1916-1925` (test pinning 30,000-file admission), `crates/codestory-retrieval/src/index.rs:1890-1993`, `sidecar.rs:329-368` · *Sweep B, CONFIRMED*

Both the stored and current inventory checks cap at 25,000 files and return `NotChecked(BoundedInventory)` *before* any mtime or hash comparison. `index_freshness_admits_operation` returns true for exactly that cause, and it is the gate for every public operation both before and after the build, as well as the activation staleness test — so activation neither reindexes nor blocks. The fail-open is deliberate (the comments at `services.rs:678-680,781-785` reason that blocking would rebuild forever without changing the answer), but nothing downstream repairs it. CLI readiness explicitly excludes `BoundedInventory` from `freshness_requires_refresh`, and the packet answer annotates only when status is exactly `Stale`.

The sharpest part is in retrieval. `compute_sidecar_input_fingerprint_with_lexical_source` hashes lexical documents read **live off disk** together with symbol and dense-anchor rows read from the **un-reindexed core**. Editing one file changes only the lexical half, so finalize logs "manifest is stale; rebuilding" and republishes a manifest whose fence recomputes the same mixed fingerprint. Afterwards `strict_readiness_unavailable_reason_for_runtime` matches and returns `Ok(None)` — so the workspace drift probe at `sidecar.rs:342-368`, the one check that would have caught the edit or deletion, is never reached. Note the inverse: if the sidecar is *not* rebuilt, strict readiness fails closed on any hash change. The fail-open depends on the rebuild happening.

**Consequence:** on any repository past the bound, edit or delete a file and the next tool call serves pre-edit symbol/line/dense evidence bound to current file text, with readiness reporting ready and no stale verdict anywhere. **Fix:** a typed unknown/degraded state that cannot claim sufficiency, or scalable persisted freshness. **Done when** a 25,001-file fixture detects an edit and a deletion, and never binds current lexical text to stale core rows.

**CR-002 — Common Svelte syntax makes components permanently `complete=false`, so their stale symbols are never deleted** · `crates/codestory-indexer/src/template_pipeline.rs:64-90` (style bodies excluded from the keep-list), `:199-222` (`collect_svelte_inline_expressions`), `crates/codestory-indexer/src/lib.rs:20271` (`complete = !has_error`), `:16704-16772`, `:1295-1310` (incomplete branch preserves the old projection) · *Sweep A, CONFIRMED; scope corrected in rev. 2 (was "Svelte/Vue/Astro")*

`prepare_template_source` puts `<script>` bodies into `keep_ranges` but `<style>` bodies into a *separate* vector, and the Svelte-only inline-expression scan uses the script ranges as its sole exclusion list — so every balanced `{...}` region outside a script survives into the blanked JavaScript. Any surviving region that is not itself valid JS yields ERROR nodes, `complete` is false, and `index_template_file` never overrides it. The incremental branch then takes the `!file_complete` path on every refresh, whose comment reads "preserve the last verified projection" — it deletes nothing while the new partial nodes are upserted additively. Renamed and deleted symbols persist as ghosts indefinitely, and the file reports partial coverage forever.

Corrected scope. The verified triggers are Svelte block syntax (`{#if}`, `{:else}`, `{/if}`, `{@render}` — `#`, `:`, `/`, `@` at statement position), spread attributes (`{...restProps}`), and CSS rule bodies containing real CSS (hyphenated properties, unit literals, `var(--x)`, `@media`, `:global`). A style block alone is *not* sufficient — `{ cursor: pointer; }` parses as a JS labeled statement — and plain mustaches and script-only components are unaffected. Measured against the 276-file Svelte 5 corpus vendored in this repo: 192 files carry block syntax, 46 more spread attributes, 1 more erroring CSS — **~86% guaranteed permanently partial**. And **Vue and Astro do not take this path at all**: `collect_svelte_inline_expressions` is gated on `TemplateKind::Svelte`, and their non-script content — `{{ }}` interpolations and style bodies included — is blanked to spaces. (Astro reaches the same end state by a different mechanism — CR-071.) **Fix:** exclude style ranges and `{#…}`/`{:…}`/`{/…}`/`{@…}` blocks from the inline-expression scan, or compute `complete` from the kept script regions rather than the whole blanked parse. **Done when** editing a Svelte component with an `{#if}` block removes its deleted symbols on the next incremental index.

**CR-003 — Whole-file lexical matches are attributed to an unrelated symbol** · `crates/codestory-retrieval/src/lexical_index.rs:893-900` (documents with `node_id`/`symbol_name`/`start_line` all `None`), `lexical_client.rs:47-57`, `crates/codestory-runtime/src/agent/retrieval_primary.rs:1761-1765`, `crates/codestory-store/src/storage_impl/mod.rs:10939,10963` (BTreeMap ordering), `search_scoring.rs:315-397` · *Sweep B, CONFIRMED*

`build_lexical_shard` emits one document per workspace source file with no node id, symbol name, or line; the nulls persist through the schema, survive the search query, and are copied verbatim into the candidate. Nothing filters it — `is_phantom_sidecar_hit` only rejects `lexical:`/`semantic:`/`scip:` prefixes, and the ranker merely assigns `definition_quality = 0.45` when the symbol name is absent. In `resolve_candidate_node_id`, both the `node_id` and `start_line` branches are skipped and the symbol-matching block is bypassed, so control reaches the tail: `nodes.into_iter().find(|(_, kind)| !matches!(kind, FILE | UNKNOWN))`. The store accumulates into a `BTreeMap` keyed on node id, so "first" is the deterministic lowest node id. `build_search_hit` then renders that node's real name and line.

**Consequence:** a token that occurs only in function B produces a citation naming function A at A's line. Node-level dedup can subsequently discard a legitimate A candidate in favour of the fabricated binding. **Fix:** keep a whole-file hit as file/range evidence using FTS offsets, or bind it to the file node as a text match — never synthesise a symbol. **Done when** a two-function fixture with a unique token in the second cites that range or the file, never the first symbol.

**CR-004 — Every ordinary hit is stamped as graph proof before its retrieval lane is known** · `crates/codestory-runtime/src/search_scoring.rs:357-395` (literal struct sets `ResolvedGraph`, producer `route_endpoint`, `Resolved`, `eligible_for_sufficiency = true`, `score_breakdown: None`), `agent/retrieval_primary.rs:1830-1838` (breakdown attached *after*), `agent/packet_evidence.rs:113-146` (decorator short-circuits on existing tier), `:81-95` (eligibility) · *Sweep B, CONFIRMED*

For any node without a structural text unit and without an `openapi:endpoint:` canonical id, `build_search_hit` hardcodes the strongest possible evidence values while `score_breakdown` is still `None`, then calls the decorator. In production the order is: build hit → attach score breakdown → decorate. The decorator's first act is `if let Some(tier) = hit.evidence_tier { return tier; }`, so the branches that would classify `DenseSemantic` or `SyntheticSourceScan` are unreachable and the second decorate call is a no-op. The breakdown genuinely would have said `DenseSemantic`: `export_rank_features` forces `scip_distance = 0.0` for candidates without graph provenance, producing exactly the (semantic > 0, lexical ≤ 0) shape the decorator classifies as dense.

The focused tests are false reassurance. They build the hit with tier/producer/resolution/eligibility all `None` and `score_breakdown` already `Some`, then decorate — the reverse of production. `score_breakdown_does_not_export_graph_for_pure_dense_candidate` therefore asserts on a hit shape the product never constructs, and passes. **Fix:** build a neutral hit, attach provenance, decorate once. **Done when** a production-path fixture proves lexical → `LexicalSource`, dense → `DenseSemantic` and ineligible, real graph → `ResolvedGraph`, with accurate producer names.

**CR-005 — The stage named "SCIP graph expansion" traverses no graph edges** · `crates/codestory-retrieval/src/scip_client.rs:168-191`, `scip_index.rs:122-133,154-155,330`, `planner.rs:37`, `executor.rs:872-878`, `ranker.rs:175-179,199-204,215-219` · *Sweep B, CONFIRMED*

Stage 2 loops over up to four anchors, linearly scans every symbol row in the repo-wide artifact for each, requires only `symbol.path == anchor.file_path`, and treats **bidirectional substring containment of display names** as the edge test. It reads no references, no edges, no target symbols — `index.proofs` is never touched, and no store query is made. The artifact could not support traversal anyway: `ScipProofRecord::definition` hardcodes `role: "definition"` and `target_symbol: None`, and `has_required_proof_records` returns `true` unconditionally, so the records are never even validated.

Yet the planner labels the stage `graph_neighbor`, the executor stamps that provenance on every hit, and `candidate_has_graph_provenance` matches it — giving `scip_distance = 0.5` at hop 1 instead of the 0.2 non-graph floor, which `export_rank_features` then deliberately preserves precisely *because* graph provenance is present. `Client`/`ClientConfig`, `run`/`runtime`, and `handle`/`handle_request` all qualify as proof-bearing neighbours. The early exit only fires after `limit` hits accumulate, so when matches are sparse — the common case, since same-file is required — all four passes scan the entire symbol list. **Fix:** remove graph-evidence eligibility from this heuristic; use real adjacency or validated imported SCIP references. **Done when** a same-file substring pair with no edge yields no stage-2 neighbour, and a real edge does.

**CR-006 — Discovery silently skips every hidden directory, so the contracted GitHub Actions collector is unreachable** · `crates/codestory-workspace/src/lib.rs:951-953` · *Sweep A, CONFIRMED*

The one production directory walker is built with only `follow_links(true)` and `require_git(false)`. `hidden(false)` appears nowhere in the repository, and `ignore` 0.4.25 defaults to `hidden: true`, returning `Match::Ignore` for any dot-prefixed entry — so `.github` is pruned at depth 1 and its subtree is never enumerated. The default synthetic manifest roots at the repository root, so `.github/workflows/*.yml` cannot reach the file inventory or the refresh plan.

The capability it kills is contracted and advertised: `language_support.rs:196-207` declares the `github_actions_workflow` collector, `is_github_actions_workflow_path` exists at `:485-500`, the indexer routes to it at `structural/mod.rs:99-101`, and coverage is promised to users in `docs/users/what-to-expect.md:19-21` and `docs/architecture/language-support.md:65`. Every other dotfile source (`.gitlab-ci.yml`, `.eslintrc.json`) is dropped the same way, with no inventory issue recorded. The synthetic manifest's explicit `**/.git/**` exclude suggests the authors did not believe dot-directories were already pruned. **Fix:** `builder.hidden(false)` plus the existing exclude patterns, or at minimum re-include `.github/workflows`. **Done when** a `.github/workflows/ci.yml` fixture is discovered and indexed.

**CR-007 — Template re-canonicalization keys symbol ids by basename, merging symbols across same-named files** · `crates/codestory-indexer/src/lib.rs:16744-16751`, `:15794-15822,15836` · *Sweep A, CONFIRMED*

`index_template_file` computes both the basename and the full file identity, then passes the **basename** as the `file_name` argument to `canonicalize_nodes_with_file_identity` and the identity only as the second argument — which is used solely for the `FILE` node branch. Every other node is re-derived as `format!("{file_name}:{qualified_name}")` (or with `:{start_line}` for callables), hashed to a node id by FNV-1a. The filter that would preserve an existing canonical id keeps only `openapi:endpoint:`/`route_endpoint:`/`tauri:command:`/`payload:collection:` prefixes, so ordinary symbols are overwritten. The regular `index_file` path passes the full identity and is unaffected.

**Consequence:** in any framework with convention-based filenames — SvelteKit `+page.svelte`, Nuxt/Vue `index.vue`, Astro `index.astro` — `interface Props` in `src/a/index.vue` and `src/b/index.vue` hash to the same id, and the store's `ON CONFLICT(id) DO UPDATE` silently merges them. Edges and occurrences from both files attach to one node. **Fix:** pass `&file_identity` (already computed one line earlier) as the `file_name` argument. One-line change; the done-condition is two same-basename template files producing distinct nodes.

**CR-071 — Astro typed frontmatter is parsed with the JavaScript grammar, landing every such file in the same never-clean-up path** · `crates/codestory-indexer/src/template_pipeline.rs:67,192-196`, `crates/codestory-indexer/src/lib.rs:16710-16713`, `:20271`, `:1295-1310`; test masking at `template_pipeline.rs:435-459` · *Split out of CR-002 in rev. 2, where it had been mis-attributed to the brace mechanism; the full retention consequence was traced during cross-check verification (single-trace provenance)*

`script_language` defaults to `"javascript"`, and the frontmatter branch upgrades to TypeScript only when the frontmatter body literally contains `lang="ts"` — a script-*tag* attribute that never appears in Astro frontmatter. Astro frontmatter is TypeScript by convention (`interface Props` is the documented component idiom), so `interface`, type annotations, and `import type` produce ERROR nodes under the JS grammar, `complete` is false, and the file enters exactly CR-002's retention path: stale symbols are never deleted. The repo's own Astro test hides this by hardcoding `get_language_for_ext("ts")` instead of consuming `prepared.script_language`, and never asserts on the selected language (the Vue test does). Filed High on parity of consequence with CR-002 — the trigger, typed frontmatter, is the norm in Astro projects. **Fix:** parse Astro frontmatter as TypeScript unconditionally, and make the test consume `prepared.script_language`. **Done when** an `.astro` fixture with `interface Props` indexes `complete=true`.

### Correctness

**CR-008 — Any position-shifting edit forces whole-file projection replacement** · `crates/codestory-indexer/src/lib.rs:21068-21079,21283-21301` · *Sweep A, CONFIRMED.* The per-callable `signature_hash` is `hash(symbol_key, start_line, start_col)` — positional. Inserting one line above any function flips it and routes the entire file to `FullReplace`, so the cheap `Delta` path survives only for edits that shift nothing (same-line changes, or edits after the last symbol). This is also the trigger mechanism for the architecture review's ARCH-001 bookmark deletion, and the reason that finding is deterministic rather than an edge case. **Fix:** hash the callable's signature text, not its position; carry position as separate metadata.

**CR-009 — Java/Kotlin methods whose leading annotations carry argument lists parse those arguments as their parameter list** · `crates/codestory-indexer/src/lib.rs:14676-14699`, string twin at `:12321-12344`, callers at `:10013` (Java), `:12052` (Kotlin), `:12291-12319` (Kotlin primary constructors) · *Sweep A, ADJUSTED twice (was High; scope narrowed again in rev. 2).* `signature_parameter_surface` takes `trimmed_node_text(callable)` and finds the first `(`; verified against the vendored grammars, leading annotations sit inside that text for Java `method_declaration` and Kotlin `function_declaration`/`class_declaration`. The rev. 1 claim that this "fires on every annotated method" was wrong: bare marker annotations — `@Override`, `@Test`, `@Inject`, `@Autowired`, the majority case on methods — carry no parentheses, so the first `(` is the real parameter list and extraction is correct. The trigger is a leading annotation *with an argument list*: `@SuppressWarnings("unchecked")` yields one token and fails the `tokens.len() < 2` guard, `@Transactional(readOnly = true)` leaves one token after the `=` split, and one argument-carrying annotation anywhere in the modifier list suffices — so Spring MVC mappings (`@GetMapping("/users")`), Spring Data `@Query`, JPA-annotated Kotlin data classes, and `@Throws`/`@OptIn` code are hit reliably. Re-verification added three sharpenings: Kotlin `::class` arguments produce a *bogus non-empty* receiver map (`{IOException: "class"}`) rather than an empty one; an annotated Kotlin data class loses all primary-constructor property bindings (`@Table(name = "users") data class User(...)` → empty binding list at `:12309`); and — a separate defect on the same path — Java *parameter-level* annotations pollute the owner type even when extraction succeeds (`f(@RequestParam("id") String id)` records owner type `@RequestParam`, `:15197-15201`). The failure everywhere is silent loss of a resolution upgrade, not a wrong edge. **Fix:** use `child_by_field_name("parameters")` (Java — a required field) / the `function_value_parameters` and `primary_constructor` children (Kotlin) instead of text scanning.

**CR-010 — Kotlin trailing-lambda and chained calls lose receiver resolution** · `crates/codestory-indexer/src/lib.rs:14939` · *Sweep A, CONFIRMED.* `kotlin_member_call` misparses the two most idiomatic Kotlin call shapes, dropping receiver resolution for `apply {}`/`let {}`/`run {}` chains.

**CR-013 — HTML collector picks anchor parents from HashMap iteration order, so edges are nondeterministic** · `crates/codestory-indexer/src/structural/html.rs:23-24,47,70-74`, `structural/common.rs:236-248` · *Sweep A, CONFIRMED.* `region_nodes.values().last()` and `id_nodes.values().next()` over `std::collections::HashMap` with `RandomState` — arbitrary between runs and even between two indexings in one process, whenever the file has ≥2 region lines. **CR-014 — Ancestor and global gitignore rules exclude tracked files from discovery, silently deleting indexed rows** · `crates/codestory-workspace/src/lib.rs:951-953` · *Sweep A, ADJUSTED twice.* `require_git(false)` with `git_ignore`/`git_global`/`git_exclude`/`parents` left at their defaults disables the repository boundary entirely in `ignore` 0.4.25 (`check_vcs_dir` is false, so `has_git` is never true). Two consequences. Every ancestor `.gitignore` above the workspace root is applied inside genuine git repositories, where git itself stops at the repository boundary. And both ancestor and global (`core.excludesFile`) rules remove matching files from *discovery outright* — including tracked files, which git's own ignore semantics never touch (ignore rules only ever affect untracked files). Matching files vanish with **no** `WorkspaceInventoryIssue`, so the inventory stays `Complete` and refresh planning schedules removal of every previously indexed row for those files. A user whose global excludes pattern happens to match tracked code silently loses it from the index. (Correction from cross-review: the original wording implied git applies no global excludes inside a repository; it does — to untracked files. **CR-039 — `node_details` loads the entire edge table to find one node's handler edge** · `crates/codestory-runtime/src/controller_symbols.rs:393`, `crates/codestory-store/src/storage_impl/mod.rs:6258,11534` · *Sweep A, CONFIRMED.* `get_edges()` is `SELECT ... FROM edge` with no `WHERE`, materialised into a `Vec`. It runs on every route-endpoint `node_details` request (both metadata builders always initialise `handler: None`) and once per route node in `affected_route_impacts`. The per-node accessor `get_edges_for_node_id` already exists and the supporting indexes are present.

**CR-040 — The full symbol-name map is cloned per resolution query** · `crates/codestory-runtime/src/controller_symbols.rs:142-151` · *Sweep A, CONFIRMED.* One `String` per canonical search symbol, cloned under lock on every `resolve_indexed_symbol_candidates` call, when consumers do at most 50 per-id lookups. The adjacent `cached_labels` helper already demonstrates the selective-lookup fix.

**CR-043 — Refresh planning SHA-256-hashes every unchanged file on every incremental plan** · `crates/codestory-workspace/src/lib.rs:1361-1378` · *Sweep A, cost CONFIRMED; original fix withdrawn in rev. 2 as invalid; recorded as ARCH-002 evidence, not counted as a separate register entry.* The cost is real and the path is hot — `plan_index_freshness` drives `stored_file_needs_index` on every freshness check, and the hash at `lib.rs:1374` runs precisely when mtime *matches*, because it is the entire content-verification mechanism (an mtime mismatch short-circuits without hashing). The originally proposed "trust mtime+size" fix is rejected on three verified grounds: stored file state carries no size field anywhere (`contracts/workspace.rs:57-65`, store `schema.rs:45-55`), so it is not even implementable without a migration; same-mtime drift detection is a deliberately defended invariant — `incremental_refresh_detects_changed_content_with_matching_mtime` (`lib.rs:2391-2421`) constructs its two file contents at *identical length*, so even mtime+size would pass stale content and the test would fail, and three indexer tests (`overwrite_preserving_mtime` family) pin the same invariant one layer down; and the hash is not a redundant double-check to be skipped but the verification itself. **Safe fix:** keep the hash as the verdict and cache the *verdict* — a session-bound memo keyed `(path, mtime, stored_content_hash)`, invalidated when re-indexing changes the stored hash; size is usable only as a positive change signal (a mismatch proves drift; sameness proves nothing). Cache insertion must respect the torn-read guard in `current_content_identity` (`lib.rs:1397-1399`).

**CR-044 — Provisioning does multi-hundred-MB synchronous work on the event loop that serves "preparing"** · `plugins/codestory/scripts/codestory-mcp.cjs:1009` · *Sweep A, CONFIRMED.* The same loop must answer MCP `preparing` responses; synchronous hashing and extraction block them.

**CR-045 — The lock waiter defeats its own identity-probe throttle** · `plugins/codestory/scripts/codestory-mcp.cjs:1529-1605` · *Sweep A, ADJUSTED.* While another launcher holds the provisioning lock, `acquireManagedCliLockAsync` re-enters every ≤50 ms for up to ~61.5 minutes. `nextIdentityCheckAt` is a **per-call local**, so the intended 2-second throttle never engages across iterations: every tick redoes a `spawnSync` process-identity probe (`/bin/ps` on macOS, `powershell.exe` on Windows), two `readdirSync` scans, a file create/delete, and a second identity probe for the lock owner — all synchronously, on the loop serving `preparing` responses. **Fix:** hoist the throttle deadline outside the retry loop.

## 5. Refuted and withdrawn

Four candidates from Sweep A did not survive verification. Recording them because the reasons are instructive.

**Withdrawn — grounding-snapshot invalidation outside the mutation transaction.** The mechanical observation was correct (`tx.commit()` at `mod.rs:11295` is followed by `invalidate_grounding_snapshots()` in autocommit, and the same shape appears at six other sites). The consequence was not: **none of these mutations run against the live database in production.** Every production caller writes to a private staged snapshot — incremental clones live→staged, full refresh opens a disposable build, semantic republish uses the staged store — and every other apparent caller is inside `#[cfg(test)]`. Two further guards close the window even inside the staged database: the run marks snapshots dirty *before* the first mutation, and a crash abandons the staged file entirely. What remains is a hygiene inconsistency with no reachable failure.

**Withdrawn — Rust turbofish calls emit a self-loop CALL edge.** The edge really is constructed with `source == target` (`lib.rs:5130-5135`), but a downstream stage the finder never checked rewrites it: `apply_line_range_call_attribution` computes `let placeholder_source = edge.source == edge.target;` — the variable name shows the self-loop is a *deliberate placeholder convention* — and reassigns the source to the innermost callable containing the call line. The persisted edge is `run → pair`, exactly what the finding claimed was missing.

**Withdrawn — the 1500 ms primary cap guarantees a semantic miss after every idle exit.** The finding rested on a grep concluding that `ensure_resident`/`acquire_residency_lease` are called only by the qualification harness. That grep missed the wrapper chain. Every product query runs inside a `PinnedQuerySession`, and `PinnedQuerySession::begin` calls `acquire_product_embedding_residency_for_runtime` (`query.rs:177`, with a comment saying exactly why), which connects with spawn-allowed intent under the 564-second bulk budget — not the 1500 ms retrieval budget — and holds a lease that pins residency so the idle timer cannot fire. **This error is worth naming**: it is the same failure mode as the ARCH-000 severity mistake in the architecture review — reasoning confidently from an incomplete search rather than tracing the call chain. The *separate* accuracy defect in the same constant (the advertised budget being silently clamped down) survives as CR-033.

**Flagged, not confirmed — the sequential rerun loop cannot recover two lost jobs in one run.** Every in-repo fact checks out: the loop is sequential under `set -euo pipefail` with no per-id tolerance, the planner can emit several ids, and three accelerator proofs start concurrently on hosts that share a physical machine. The decisive fact — whether GitHub rejects a rerun POST for a second job once the first has put the run back in progress — is external API behaviour that cannot be established from the repository. Treat as an open question; CR-018 fixes the adjacent planner defect regardless.

## 9. Coverage and method limits

**Read line-by-line:** `codestory-store/storage_impl/mod.rs` (all 11.7k non-test lines) and `schema.rs`; `codestory-workspace` (`lib.rs`, `repository_identity.rs`, `paths.rs` in full); `codestory-contracts` (`dto.rs`, `errors.rs`, `language_support.rs`, `types.rs`, `ids.rs` in full); `codestory-llama-sys` (`lib.rs`, `admission.rs`, `build.rs`, `model_staging.rs`, `native_staging.rs`); `codestory-runtime` non-agent modules (`services.rs`, all `controller_*.rs`, `index_incremental.rs`, `index_full.rs`, `search_plan.rs`, `search_publication.rs`) and the agent plumbing (`packet_budget.rs`, `packet_batch.rs`, `packet_trace.rs`, `trace.rs`, `retrieval_primary.rs` production half); `codestory-retrieval` (`generation.rs`, `inventory.rs`, `sidecar.rs`, `mode.rs`, `config.rs`, `retention.rs`, `query.rs`, `cache.rs`, `lexical_index.rs`, `embedded_vector.rs`, `planner.rs`, `executor.rs`, `per_user_embedding/*`); `codestory-cli/stdio_transport.rs` (first 6.1k lines), `runtime.rs`, `config.rs`, `args.rs`; both launcher scripts in full; the full constants chain and all user/contributor docs.

**Sampled rather than exhausted:** the indexer's 27.8k-line `lib.rs` — four language regions (Rust, Python, TypeScript, Kotlin) plus the HTML and SQL collectors were read closely; the remaining twelve languages were not. `orchestrator.rs` was read in segments, not end to end. CI scripts were spot-checked (five of the most load-bearing).

**Not audited:** GGUF/model-file parsing as an attack surface, tree-sitter grammar C code, most TUI presentation, `codestory-bench` internals, Windows-specific hook behaviour, and actual CI run history.

**Method limits worth stating.** Everything here is static. No test was executed and no packet was run, so every claim about runtime behaviour is a code-path conclusion — the pass counts, scan counts, and commit counts are derived from call-site structure, not measurement. Three consequences follow. First, the performance findings state *what work is performed*, not what it costs; CR-034, CR-036, and CR-043 all deserve measurement before they are scheduled against each other. Second, one finding (the sequential rerun loop) turns on external API behaviour and could not be resolved at all. Third, and most instructive: of the four Sweep A candidates that verification killed, two died because the finder stopped tracing one call too early — a downstream stage that rewrote the edge, and a wrapper chain a grep missed. Both had been reported at high confidence. Any future pass on this codebase should treat "I grepped for the callers" as the beginning of the argument rather than the end. The revision 2 cross-check proved the point in both directions: CR-016's original consequence died at a persistence-layer fence one call past where its verifier stopped, and the cross-check's own counter-claim ("cannot be republished as healthy") turned out to have two blind spots visible only by reading what that fence actually parses — `index.scip` is existence-checked, never content-checked.
