## 1. System Snapshot

**What it is.** A local code-intelligence product for coding agents, v0.16.3: one Rust executable that turns a checkout into a cited graph plus retrieval evidence, served over stdio MCP to agent hosts (Codex, Cursor, Claude Code, Copilot) via a Node plugin. Tree-sitter parses 16 languages into a SQLite core graph (`codestory.db`); immutable retrieval "generations" (FTS5 lexical index, embedded-llama.cpp CodeRankEmbed Q8 vectors in SQLite, SCIP) bind to one core publication; a runtime crate orchestrates; answers fail closed on stale or partial evidence.

**Scale.** 339,429 lines of Rust (including tests) across 9 workspace crates; a 3,782-line Node launcher in `plugins/codestory`; 9,143 lines of vendored `tree-sitter-graph`; and ≈101k lines of CI/release machinery (9,065 of workflow YAML across 23 workflows, 56,778 in `.github/scripts`, 35,726 in `scripts/`). Largest files: `crates/codestory-indexer/src/lib.rs` (27,852), `crates/codestory-runtime/src/agent/orchestrator.rs` (14,533), `crates/codestory-store/src/storage_impl/mod.rs` (12,280), `crates/codestory-cli/src/stdio_transport.rs` (8,169).

**Runtime topology.** Host → `.mcp.json` → Node launcher (provisions/verifies a pinned CLI release, serves a fail-open "preparing" MCP while downloading, then replays the initialize frame into `codestory-cli serve --stdio --multi-project`). The Rust server is a strictly serial loop: one request at a time in a `spawn_blocking` worker, per-request project selection into an LRU of 1 active + 3 retained `RuntimeContext`s (capacity 4 total, `stdio_transport.rs:57-58`; eviction after active installation leaves at most `capacity - 1` retained — corrected in rev. 6, was stated as 1 + 4). One per-user embedding server is elected across all CodeStory processes (Unix: `flock` authority + 0600 socket published by atomic rename; Windows: first-pipe-instance seal + explicit DACL), runs one native llama.cpp worker, and exits after 60 s idle. ~20 `CODESTORY_PLUGIN_*` env vars form the plugin↔CLI contract.

**Data topology.** Per-project cache: staged→published `codestory.db` behind a journaled, flock'd promotion fence (SQLite backup/restore, not rename); retrieval sidecars in per-generation directories keyed by publication generation id, with the manifest (current + rollback pointer pair) inside the core DB so a whole-DB restore atomically binds both. Schema migrations are sequential in-code v2→v30+, forward-only, fail-closed on newer versions.

**Deployment.** Two-branch flow (`dev/codestory-next` → `main`; PR source guarded). Pushing a version bump to `main` auto-publishes: `auto-release.yml` routes to `release.yml` (native lane) or `plugin-release.yml`. Release gates are a formal machine-checked "claims/evidence" system (`release-claims.json`, 1,587 lines: 8 claims, 7 proof tiers, identity binding, 168-hour validity windows, recorded non-claims) with builds on GitHub-hosted runners and accelerator proofs on three single self-hosted machines. Pre-merge proof is mostly human-dispatched with hand-copied SHAs/digests.

**People.** 1,604 of 1,608 commits are one author; ~1,500 commits in the last 3 months. Development is heavily agent-mediated (elaborate `AGENTS.md`, worktree scripts, saga/issue guards).

## 2. Critical paths (Phase 1, condensed)

1. **MCP request path** (plugin → `stdio_transport.rs` → orchestrator). Well-designed partial-readiness surface (`codestory_preparing` with `retry_after_ms`, recommended next calls, diagnostics URI). Defects: host cancellation masked for tool bodies (ARCH-011); double public-operation wrapping re-runs freshness scans (feeds ARCH-002); split error contract (ARCH-019); substantial business logic in the transport (ARCH-017).
2. **Index write path** (workspace → indexer → store). The promotion fence is the strongest engineering in the repo: fsync'd prepared journal, `Connection::restore` at `synchronous=FULL`, post-restore identity re-validation, crash recovery on every open, tested by cross-process fault injection. Defects at the fence's *edges*: bookmarks bypass it (ARCH-001); three full DB copies per incremental publish (ARCH-013); the 27.8k-line indexer god file (ARCH-012).
3. **Retrieval query path** (pin → validate → execute → revalidate). Fail-closed admission is real and multi-layered; bounded single retry on `publication_changed`. Defects: O(repo) readiness recomputation per call (ARCH-002); heuristic retrieval-completeness accounting with a verdict-blind primary shadow (ARCH-016); ~8.4k lines of benchmark-fitted claim/sufficiency heuristics (ARCH-005).
4. **Embedding server lifecycle.** Election, idle-drain, and admission protocols are sound under adversarial interleaving (independently re-verified). Defect: the watchdog cannot see query-class native hangs (ARCH-010); the server process has no log sink (part of ARCH-006).
5. **Bootstrap/provisioning.** The Node launcher is the most defensively engineered code in the repo (resumable inode-checked downloads, hardened extraction, staged verification incl. a real MCP handshake probe, atomic publish, quarantine). Defect: the trust root is GitHub TLS only — the archive-digest pin field ships empty and nothing verifies signatures client-side (ARCH-015).
6. **Release topology.** The claims/evidence system demonstrably prevents overstated release notes (Ripgrep failed preregistered recall thresholds → v0.16 ships no Rust packet-quality claim). Costs: ~101k lines of machinery, triple-artifact pipeline changes, tribal choreography, dead perf-evidence host (ARCH-007, ARCH-008, ARCH-009).

## 4. Architecture verdict

CodeStory is optimized for one thing above all: **provable correctness of derived state on a single user's machine, maintainable by one person working through coding agents.** Nearly every unusual decision follows from that objective. The publication fence rebuilds and *restores* SQLite databases instead of renaming files so that recovery can be validated identity-by-identity on every open. Retrieval readiness is re-derived from first principles on every query rather than trusted from a flag. Releases publish only claims that a machine-checked evidence graph can bind to real hardware runs, and when a proof host is lost the release ships a recorded non-claim instead of a silent gap. Architecture rules, catalog parity, and even benchmark-fitting debt (183 inventoried corpus markers with a CI ratchet) are executable checks, because with 1,604 of 1,608 commits from one author, process is doing the work reviewers would do elsewhere. Within its threat model the security work is over-delivered, not under: three-layer IPC authentication, hostile-repo config boundaries with tests, hardened archive extraction.

That optimization matches what the product needs — a grounding tool whose value is that its answers can be trusted — and the three load-bearing decisions are sound: (1) SQLite-everything with a journaled copy-based promotion fence; (2) a single elected per-user embedding server amortizing one warm model across all projects; (3) the claims/evidence release regime. I would preserve all three.

Two blind spots cut across that otherwise-disciplined posture, and both were found only by cross-checking a second review. The first is that **the threat model covers repository *content* but not repository *metadata*.** The team explicitly designed and tested a boundary preventing a repo's `.codestory.toml` from redirecting caches or endpoints — genuinely good work — while `RuntimeContext` construction shells out to `git` three times against that same untrusted repo with no environment or config constraint, on every project-scoped request, before any content is read (ARCH-000). The exposure needs attacker-controlled `.git` metadata, which a normal clone does not supply, so it is High rather than Critical — but the care taken over one channel makes the omission of the adjacent one more striking, not less. The second is that **the system's central product claim — that a `sufficient` packet's `proven` claims are safe to act on without opening the files — is not backed by the evidence semantics it advertises** (ARCH-036). Behavioral roles are inferred from display-name and path substrings, templated into factual sentences, and marked `Proven` on citation resolvability alone; `unsafe_to_claim=false` and an `avoid_opening` list follow from a count-based verdict. Both are failures of the same kind the architecture is otherwise excellent at preventing: an unproven thing presented as proven.

Beyond those, the bill for this posture comes due in three places. First, **correctness rigor stops at the process boundary with operations.** The system can prove a publication is coherent but cannot tell you what it did: 45 tracing call sites across 340k lines with no subscriber installed anywhere, no panic hook, a bare-`abort` fail-stop, and crash evidence discarded at every layer. The same asymmetry produces the liveness holes — blocking file locks with no timeout, joins with no deadline, a watchdog that cannot see the one hang class that matters — and the absence of any field kill switch, so a semantic-lane failure disables even the healthy lexical lane with no operator recourse. The system is engineered never to lie, and accepts wedging, dying silently, or refusing service as the price; in the field, users experience that as "it stopped working and nothing says why."

Second, **the fail-closed re-derivation habit is applied without cost accounting.** A single packet call re-reads and re-hashes unchanged repo content ~7–10 times and rescans full tables ~14–20 times (statically counted call sites on the worst path) before doing retrieval work, inside a strictly serial request loop; the vector stage is a scalar full scan per subquery. None of it is instrumented, so the degradation arrives silently as repos grow — the stage budgets convert overload into quietly worse answers rather than visible latency.

Third, **the single largest structural risk is concentration: bus factor 1 amplified by calibration and process nobody else can operate.** The release choreography lives as AGENTS.md prose plus hand-copied digests; answer quality rests on ~8.4k production lines of benchmark-repo-fitted string heuristics whose fire rate on real-world repos is unmeasured; the performance-evidence lane targets a runner that no longer exists; and ~101k lines of CI machinery absorb 20–30% of all commits. Every one of these is individually defensible; together they mean the project's ability to ship, and to know its answers are good, currently resides in one person's working memory. If only one investment can be made this year, it should be converting that memory into executable form — a release driver script, data-driven claim contracts with generalization evals, and enough observability that a stranger can diagnose a field failure.

## 5. Findings register

Severities are post-verification. Confidence: **High** = code path read fully (and, for the top nineteen, independently re-derived by a verifier); Medium = partially; Low = inferred. There are no Critical findings (see revision 3 note).

### High

**ARCH-000 — Unconstrained `git` subprocesses run against untrusted repository metadata on every project-scoped request, before any content is read** · `crates/codestory-workspace/src/repository_identity.rs:118-121` (three commands) and `:863-868` (`git_output`); reached from `crates/codestory-cli/src/runtime.rs:220` (second statement of `RuntimeContext::new_with_startup`); dispatched at `crates/codestory-cli/src/stdio_transport.rs:955` (`tools/call`) and `:878` (`resources/read`) · Effort S (containment) / M (durable) · Confidence High (verified independently; mechanism reproduced with git 2.54.0).

`inspect_repository_identity_v2` runs `git config --get remote.origin.url`, `git rev-parse HEAD^{tree}`, and `git status --porcelain` via a bare `Command::new("git")` — no `-c` overrides, no `GIT_CONFIG_*`, no `env_clear`, no ownership check, and `git` resolved through `PATH`. Git honors a repository-local `core.fsmonitor` as an executable hook during `status`, so a repository containing hostile `.git/config` achieves arbitrary code execution as the CodeStory user. A repo-wide grep for `GIT_CONFIG|GIT_DIR|safe.directory|no-optional-locks|core.fsmonitor` across all Rust/JS/docs returns only a CI test harness; no git library (gix/git2) is used anywhere.

Two amplifiers raise this above a routine hardening item. (1) **It is on the hot path, not the setup path:** the call is the second statement of runtime construction, before config load, before activation, before any publication check, and is reachable from the read-only `status` tool. (2) **The shipped configuration removes the mitigation:** the plugin launches `serve --stdio --multi-project` (`plugins/codestory/scripts/codestory-mcp.cjs:1801,3582`), so `runtime.is_none()` sets `project_required = true` (`stdio_transport.rs:606`), which disables the same-path short-circuit at `stdio_transport.rs:646` — a fresh `RuntimeContext`, and a fresh triple git invocation, is built on *every* project-scoped request rather than once per project switch.

**Precondition (the limiting factor).** The attack needs attacker-controlled `.git` metadata in the selected directory. A normal `git clone` does **not** provide it: clone writes a fresh local config and initializes `remote.origin.*` itself; repository config is not carried by the Git protocol. Realistic delivery vectors are narrower — an archive or backup that includes a `.git/` directory, a working copy transferred or synced from another machine, a shared/CI checkout, or another local tool writing repository config. `safe.directory` is not a defense in any of these, since it only blocks *differently-owned* repositories and a restored or unpacked tree is owned by the user. This is why the finding is High rather than Critical: the impact is arbitrary code execution as the user, but it is not reachable through the single most common way people obtain a repository.

*Charitable reading:* `git status` is the obvious way to compute a dirty-state identity component, the code predates the multi-project launch mode that removed the caching short-circuit, and the team clearly did think about hostile repositories — they built and tested a config-boundary defense (`config.rs:139-166`). The subprocess channel simply was never enumerated as a boundary.

**Fix:** immediately add `-c core.fsmonitor=false` to `git_output` — one line, ships today, and that flag alone is the code-execution containment. (`--no-optional-locks` is worth adding in the same change so observational `status` calls stop writing the index of a repository the product is only reading — but it is hygiene, not containment: it does not prevent fsmonitor execution.) Then route every production git call through one constrained wrapper (explicit allowed-command list, cleared environment, absolute binary path, timeout, bounded output). For the per-request amplification, fix the short-circuit semantics rather than the cache: make `project_required` mean "the project argument is mandatory" instead of "discard reuse", so an unchanged active project skips runtime reconstruction. Do **not** simply wire the dead `cached_project_identity_v3` (`repository_identity.rs:191`) into these paths — its own contract restricts it to observational reads (`:187-190`: "Mutating paths must use `project_identity_v3` so dirtiness changes are observed immediately"), and caching dirtiness on mutating paths would corrupt freshness decisions. Two other production sites need the wrapper: `crates/codestory-runtime/src/cache_rehydrate.rs:316-334` and `crates/codestory-cli/src/app/source_commands/affected.rs:88-89`. Separately audit the adjacent `sh -lc` / `cmd /C` surface at `crates/codestory-runtime/src/system_actions.rs:31-34` for caller-controlled input. **Done when** a sentinel-fsmonitor repository is selected via a real MCP request and the sentinel does not execute — as a permanent regression test.

### High

**ARCH-001 — Bookmark state is coupled to disposable projections: deleted by ordinary incremental re-indexing of an edited file, erased wholesale by full refresh, and clobbered by concurrent publication** · deletion path (new in rev. 5): `crates/codestory-indexer/src/lib.rs:1295-1348` (`accept_storage` → `ProjectionUpdateMode::FullReplace`), `:21068-21079` (positional signature hash), `crates/codestory-store/src/storage_impl/mod.rs:11194-11199` (`DELETE FROM bookmark_node` for every node in the file), pinned by `storage_impl/tests/mod.rs:7908-7936`; refresh/clobber paths: `controller_bookmarks.rs:40,61,77,119,144,185`, `controller_core.rs:133-137`, `index_incremental.rs:512`, `index_full.rs:210-239`, `storage_impl/mod.rs:5508-5530` · Effort M · Confidence High (deletion mechanism surfaced by the counter-review in round 3; verified here and found *stronger* than claimed).

Three loss mechanisms, in increasing order of user surprise. **(1) Ordinary editing.** On incremental refresh of an already-indexed file, the writer picks `FullReplace` whenever any symbol is added, removed, or renamed — or whenever any callable's start position shifts, because the per-symbol signature hash embeds `start_line`/`start_col` (see CR-008 in the [code review](code-review-2026-08.md): that positional hash is itself a defect, and fixing it would shrink this trigger considerably). Nearly any multi-line edit qualifies; the surviving `Delta` path covers only position-preserving, body-only edits. `FullReplace` calls `delete_file_projection`, which deletes every `bookmark_node` row for the file's nodes in the same transaction — mechanically required, since the FK has no `ON DELETE` action and connections run `foreign_keys=ON`. Node ids are deterministic hashes of `file:qualified_name(:start_line)`, so the re-indexed symbol frequently reinserts under the *same id* — but the bookmark and its comment are already gone, and no code path anywhere in store, indexer, or runtime preserves, remaps, or re-attaches bookmarks (`add_bookmark` is reachable only from the user CRUD endpoint). The store test suite pins the destruction as expected behavior. Net: edit a file, let ordinary indexing run, lose every bookmark in it — no full refresh, no race required (the only reprieve: an incomplete re-parse preserves the old projection). **(2) Full refresh** builds a fresh DB and `copy_forward_full_refresh_artifacts` omits `bookmark_category`/`bookmark_node` — categories go too, and upgrades are exactly what force full refreshes. **(3) Concurrency:** bookmark mutations open the live DB writable with no fence (the indexing guard `ensure_consistent_read_state`, `controller_core.rs:272-279`, covers Files/Search/Grounding/Affected, never bookmarks); incremental clones live→staged at start and promotes whole-DB with a journal that replays nothing, so mid-run creates/updates are lost and mid-run deletes resurrect.

The deletion in (1) is deliberate referential-integrity cleanup, not an accident — but nothing in code or comments weighs remapping user annotations to the reinserted (often bit-identical) node ids instead of destroying them, while the adjacent incomplete-parse branch *does* carry an explanatory preservation comment. This is an active data-ownership defect — user-authored state stored in a derived artifact with the derived artifact's lifecycle — not an edge-case refresh bug. **Fix:** move user annotations to a sidecar DB keyed by stable symbol identity that neither promotion nor projection replacement touches; staged-replay or write-fencing alone cannot fix mechanism (1). **Done when** contract tests prove bookmarks *and categories* survive all three: a position-shifting edit through ordinary incremental refresh (the same-id reinsertion case), a full refresh, and concurrent create/update/delete during a run.

**ARCH-002 — Strict-readiness/freshness validation performs ~7–10 full repo content read+hash passes and ~14–20 full table scans per packet call** · `crates/codestory-retrieval/src/index.rs:1865-1898` (`compute_sidecar_input_fingerprint`), `lexical_index.rs:153-170`, `sidecar.rs:234-392`, `query.rs:187-197`, `executor.rs:263-301`, `codestory-workspace/src/lib.rs:1361-1401` (`stored_file_needs_index` re-hashes mtime-matched files), amplified by double public-operation wrapping (`services.rs:1112-1146`, `browser.rs:105-123`) · Effort M · Confidence High (verified statically — the pass counts are worst-path call-site counts, not runtime traces; tracing would tighten the numbers, the redundancy itself is not in doubt).
Four separately-evolving predicates guard the same invariant (one documented as merely "conservative-agreeing", `generation.rs:192-210`); each re-derives the workspace fingerprint from file *content*. O(repo bytes) × redundancy dominates packet latency on large repos, invisible because uninstrumented, inside the serial loop. **Fix:** compute strict readiness once per `PinnedQuerySession`, cache the verdict keyed by composite publication identity for the session; make enablement checks read the cached verdict; keep only the cheap health probe per query. Separately, make the workspace freshness check trust mtime+size (content hash only on mismatch). **Done when** a packet call on a warm unchanged repo performs exactly one fingerprint pass, measured by a new counter in the packet trace.

**ARCH-003 — No field kill switch, degraded mode, or rollback lever for semantic retrieval** · `crates/codestory-retrieval/src/mode.rs` (only `Full` is promotion-eligible), `query.rs`, `executor.rs:146-261`; retention keeps a rollback generation no code path activates · Effort M · Confidence High (verified).
Any semantic-lane failure (corrupt generation, wedged embedding server, device-policy rejection) disables *all* broad retrieval including the healthy lexical lane; recovery is reindexing or a multi-hour release. The fail-closed invariant (AGENTS.md) is the charitable reason — but fail-closed and inoperable are different things. **Fix:** an explicit, in-band-annotated degraded mode: `packet`/`search` may serve lexical+graph evidence with a `degraded: semantic_unavailable` marker under an operator flag, plus a `doctor --activate-rollback-generation` command using the already-retained rollback pointer. **Done when** a user with a corrupt vector sidecar gets cited lexical answers with an explicit degradation marker instead of refusal.

**ARCH-004 — Blocking file locks with no timeout, joined by eviction and shutdown: routine sibling publication stalls the entire pipeline** · `crates/codestory-retrieval/src/retention.rs:102-156` (fs4 `lock_shared`/`lock_exclusive`, no timeout, no cancel poll), `services.rs:643-660` (eviction joins the activation worker), `stdio_transport.rs:135-166` (EOF drain joins active request) · Effort M · Confidence High (verified).
The routine trigger is just a concurrent publication or GC in a sibling process: a multi-minute exclusive hold blocks a reader's shared acquisition, which blocks eviction, the serial loop, and process shutdown, with no cancellation recourse; a wedged holder blocks forever. **Fix:** a `try_lock`-with-deadline-and-cancel-poll wrapper in retention.rs as the only lock entry point; make eviction detach rather than join past a deadline. **Done when** every fs4 acquisition site goes through the wrapper and a test proves a held exclusive lock cannot stall shutdown beyond its deadline.

**ARCH-039 — Marketplace catalog is promoted before post-publish smoke, with no automatic rollback on failure** · `.github/workflows/release.yml:764-768` (`gh release create`), `:776-858` (`marketplace-publish`, `needs: [preflight, publish]`, pushes the catalog pin), then post-publish smoke runs afterward with no step that restores the previous catalog revision · Confidence High (verified independently).

**ARCH-040 — A self-hosted runner offline *before* job assignment escapes the bounded-recovery model** · `.github/workflows/lost-runner-rerun.yml:9-15,32` (triggers only on `workflow_run` completed-with-failure), `.github/scripts/lost-runner-recovery.mjs:87-110` (signature requires a mid-job disconnect annotation + an empty-conclusion step + absent logs), `release-claims.json` `non_claim_policy` (models mid-job loss, not never-started) · Confidence High (verified independently).

**ARCH-042 — The stdio queue is an unbounded `VecDeque` with no backpressure, and the Node relay in front of it is unbounded too** · `crates/codestory-cli/src/stdio_transport.rs:87` (`active: Option<ActiveStdioRequest>`), `:146-152` (continues reading stdin under `tokio::select!` while a request runs), `:185` (pushes every accepted frame into `queued`) · Confidence High (verified independently).

Rated Low, not Medium: the producer is a local trusted MCP host that awaits responses rather than pipelining gigabytes, so unbounded growth needs a runaway client — but the fix is a few lines. Adds the missing resource bound to the head-of-line blocking already described in ARCH-011. **ARCH-025 — Lifecycle management for on-disk state covers versions and generations, but not projects or models** · managed CLI installs *are* pruned — rev. 1 said "nothing cleans old version installs," corrected in rev. 4: the launcher retention policy `active_plus_one_verified_adjacent` runs at every healthy MCP startup (`codestory-mcp.cjs:2579-2724`) — and generations have retention at publication plus a user-invocable `retrieval inventory --apply`. **Fix:** extend the existing ownership-proof cleanup surface (`doctor --gc` or a widened `retrieval inventory --apply`) to abandoned project caches and stale model hashes.

## 6. Strengths (preserve these through any refactor)

1. **The publication fence** — journaled, identity-validated, crash-recoverable promotion with schema-level CHECK-constraint enforcement, proven by cross-process fault-injection tests that abort a child mid-stage and assert the live DB/backup/journals survive (`storage_impl/tests/mod.rs:5421-5495`).
2. **Executable architecture** — `architecture_contracts.rs` turns the crate DAG, CLI thinness, the read-only browser surface, and catalog↔service alignment into failing tests; the MCP catalog is generated by interrogating the real binary and drift-checked in CI.
3. **The provisioning launcher** — resumable inode-verified downloads, hardened two-format extraction, staged verification ending in a real MCP handshake probe, atomic publish, quarantine-and-single-reprovision, 105 tests including archive bombs and lock ABA.
4. **Local security engineering** — three-layer IPC auth (0600-by-rename socket + SO_PEERCRED + executable-SHA hello; Windows explicit DACL validated ACE-by-ACE), uniformly parameterized SQL, hostile-repo config boundary with tests proving `.codestory.toml` cannot redirect caches or endpoints.
5. **Fail-closed data admission** — derivational generation binding (a manifest cannot claim a generation it wasn't built from), composite-identity-keyed caches, current+rollback pointer pair validated on read and write.
6. **In-band agent diagnostics** — the preparing/status/diagnostics triad with retry hints, capability splits, and live embedding-server snapshots, deliberately available when bootstrap failed.
7. **The claims/evidence release regime's honesty** — preregistered thresholds that demonstrably withheld a marketing claim (Ripgrep recall), recorded non-claims for lost hosts, release notes rendered from the accepted ledger.
8. **Production panic discipline** — ~60 unwrap/expect workspace-wide outside tests; the store has zero in 12,280 lines.
9. **Concurrency protocol design** — election, idle-drain CAS, and refcounted admission verified sound under adversarial interleaving; exemplary async/blocking separation.
10. **Model vendoring** — `vendor/tree-sitter-graph` with pinned upstream, documented delta, explicit exit condition, near-zero churn.
